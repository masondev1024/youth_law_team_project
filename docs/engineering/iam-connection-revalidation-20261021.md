# IAM 연결 재사용 차단·복구 재검증

2026-10-21 개인 후속 개발에서 합성 자료만 사용해 수행한 별도 AWS 개발자 재검증이다. 검증 대상 소스는 개인 저장소 커밋 `e13428648a25674b758f49a49303530ede3ffd0c`로 고정했다. 앱 기능 코드는 바꾸지 않고 검증 절차를 보완했다. 모델 호출은 없었고, 실제 참가자 접수는 닫혀 있으며 전문가 검토는 대기 중이다.

이 기록은 [초기 AWS 리허설 결정 기록](aws-rehearsal-decisions.md)의 후속 증거다. 초기 리허설의 판단이나 결과를 소급해 바꾸지 않는다. 식별 정보를 제거한 수치는 [재검증 증거 JSON](../evidence/iam-connection-revalidation-20261021.json)에 있다.

이후 동일 프로세스의 실제 loopback HTTP 경로를 대상으로 한 별도 검증은 [HTTP IAM 차단·복구 재검증](http-iam-revalidation-20261021.md)에 기록했다. 두 검증은 대상과 관측 경로가 다르므로 결과를 합산하지 않는다.

## 문제와 선택

IAM 정책 변경 API가 성공했다는 사실만으로 기존 앱의 실제 DynamoDB 요청도 차단됐다고 볼 수 없었다. 앱 경로의 거부를 확인하고, 권한 복구 뒤에도 앱이 정상 상태로 돌아오는지 확인할 필요가 있었다.

앱과 같은 역할·테이블을 대상으로 한 새 `GetItem` 조회를 대조군으로 삼아 실제 IAM 거부를 먼저 확인한 뒤 앱의 상태 응답을 검사했다. 이 읽기 권한 차단·해제 정책은 별도 제어용 SSO 역할로 적용했다.

첫 120초 시험에서는 새 세션의 조회가 거부되는 동안 기존 연결 조회는 허용됐다. 이 짝지은 결과가 각각 22회 관찰되어 시험은 실패로 보존됐다. 이 수치는 같은 고정 자격 증명으로 만든 클라이언트 비교 횟수가 아니다.

그 뒤 별도 진단에서 기존 앱 클라이언트의 고정 자격 증명을 사용했다. 같은 자격 증명으로 만든 새 클라이언트는 거부됐고 기존 클라이언트는 허용됐으며, 기존 연결 풀을 닫은 뒤에는 기존 클라이언트의 요청도 거부됐다. 후속 최종 재검증은 차단 단계에서 기존 풀을 닫아 거부를 확인했고, 복구 단계에서도 풀을 닫아 갱신한 뒤 허용을 확인했다. 앱의 자격 증명·authority 객체·런타임 자체는 교체하지 않았다. 이는 연결 재사용과 갱신에서 관측 결과가 달랐다는 뜻이며, AWS 내부 캐시의 구체적 원인을 밝혔다는 뜻은 아니다.

## 결과

같은 런타임의 `/ops/participant-records/status` 인프로세스 ASGI 응답은 **200 → 503 → 200**이었다. 차단 단계에서는 실제 AWS 거부를 확인한 뒤 503을 관측했다. 복구 단계에서는 정책 제거 후 새 조회가 허용되는 대조 결과를 확인하고, 기존 연결의 거부도 관찰했다. 연결 풀을 명시적으로 갱신한 뒤 같은 기존 클라이언트의 허용을 확인하고, 명시적 sweep을 실행해 200을 확인했다.

AWS를 사용하는 별도 비동기 검사도 통과했다. 로컬에서는 회귀 검사 49건과 Ruff가 통과했고, opt-in AWS 검사 1건은 기본 로컬 실행에서 건너뛰었다. 해당 검사는 AWS에서 별도로 실행해 통과했다. 대기 중 다른 ASGI 요청이 처리되는지도 확인했지만, 주입된 대기 시간은 실제 AWS 지연 시간이 아니다.

시험을 마친 뒤 서비스와 타이머를 다시 시작했고 `/ready` 200을 별도로 확인했다. 종료 점검 34건에서 오류와 잔존 자원이 없었고, S3 객체 버전·삭제 마커 27개를 제거했다. EBS 볼륨 2개, EBS 스냅샷, DynamoDB 백업, Terraform 관리 자원이 남지 않은 것을 확인했다. 정리 감사 시각은 2026-10-21 08:18:37 UTC다.

## 운영 해석과 한계

이 결과는 실제 AWS 권한 호출과 인프로세스 ASGI를 연결한 조건부 검증이다. Uvicorn 소켓에 장애를 주입한 검증이 아니며, IAM 변경의 즉시·자동 반영이나 자동 복구 시간을 증명하지 않는다. 연결 풀 갱신 없이 즉시 권한이 회수된다는 보장도 없다. 서비스가 재시작된 뒤 readiness가 통과했다는 관찰 역시 별도 기록이며 앞선 ASGI 결과와 합쳐 해석하지 않는다.

운영 절차에서는 IAM 권한 변경 후 새 연결의 대조 조회와 앱 연결 갱신 또는 프로세스 교체를 계획해야 한다. 비동기 처리가 이벤트 루프의 동기 호출 차단을 줄이는 효과와, IAM 권한 변경·연결 상태는 별개로 다뤄야 한다. 이 결과는 법률 정확성, 사용자 품질·편익, 고가용성 또는 운영 SLA를 입증하지 않는다. 전문가 검토는 PENDING이고 실제 참가자 접수는 CLOSED다.

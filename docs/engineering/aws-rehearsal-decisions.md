# AWS 리허설 엔지니어링 기록

이 기록은 합성 데이터만 사용한 **초기 1회 개발자 리허설**에서 무엇을 관찰했고, 어떤 선택을 했으며, 어디까지 확인했는지 남긴다. 이 문서와 연결된 증거 JSON은 그 초기 실행의 기록이다. 이후 수행한 별도 IAM 연결 재검증의 문제·결과·한계는 [후속 기록](iam-connection-revalidation-20261021.md)과 [후속 비식별 증거](../evidence/iam-connection-revalidation-20261021.json)에 따로 정리했다. 두 기록의 관찰을 한 실행으로 합치지 않는다. AWS 자원은 각 실행 종료 후 제거했다. 실제 참여자 검증은 CLOSED이고 전문가 검토는 PENDING이다. 법률 정확성, 사용자 편익, 고가용성 또는 운영 SLA를 평가한 작업이 아니다.

공개 포트폴리오는 [jungseongheon.org/portfolio](https://jungseongheon.org/portfolio)에 게시되어 있다. 아래 연결 증거는 게시 전 시각에 기록된 안전한 요약이다. 그 안의 `public_site_updated: false`는 증거 캡처 당시 상태를 뜻한다.

## 결정 기록

각 항목은 **문제 → 관측·원인 → 대안 → 선택 이유 → 구현 → 재검증 → 한계 → 다음 트리거** 순서로 요약한다. 변경과 검증 결과를 구분하고, 한 번의 관측을 일반적인 보장으로 확대하지 않는다.

### 한 명의 개발자에게 필요한 최소 AWS 구성

- **문제:** 인증, 보관, 철회, 복원, 재시작 흐름을 실제 AWS에서 살펴보면서도 리허설을 상시 서비스로 키우지 않아야 했다.
- **관측·원인:** 초기 구상에는 공개 SSH/서비스 포트, 큰 인스턴스, 넓은 모델 권한이 포함되어 범위와 비용에 비해 컸다. 단일 개발자 부하와 상시 서비스 요구는 측정되지 않았다.
- **대안:** 다중 AZ RDS는 관리형 DB의 가용성 이점을 주지만 이 실험의 단일 작업자와 짧은 수명에는 비용과 운영 범위를 늘린다. EKS는 여러 서비스의 배포·확장이 필요할 때 가치가 있지만 여기에는 그런 워크로드가 없었다. MSK도 지속적인 이벤트 스트림과 처리량 요구가 확인되지 않아 제외했다. 비동기 작업이 실제로 생기면 SQS를, 운영 알림 채널과 수신 정책이 정해지면 SNS를 별도로 검토한다.
- **선택 이유:** 인바운드가 없는 소형 EC2 한 대에서 SQLite를 사용하고, 일관된 백업은 S3에, 최신 철회 권위는 DynamoDB에 뒀다. 운영자는 Systems Manager로 접근했다. 구성 요소를 분리해 데이터 복구와 최신 삭제 권한의 역할을 구분하면서, 이 규모에서 필요하지 않은 상시 플랫폼 비용을 피했다.
- **구현:** 실행용 Terraform, systemd 서비스·백업 timer, 앱의 클라우드 저장소 코드는 [리허설 인프라](../../infra/rehearsal/README.md), [저장·복구 코드](../../app/cloud_rehearsal.py), [권한 게이트](../../app/cloud_authority_handler.py)에 있다. 권한 모델은 앱 읽기와 좁은 Lambda 추가 경로를 분리한다. 후속 코드 리뷰에서 event loop의 직접 DynamoDB 호출 경로가 발견되어, 이 경계의 코드 구현은 별도 수정·통합 검증 대상이 됐다. 삭제 권한은 오래된 SQLite/S3 백업 안에만 두지 않는다.
- **재검증:** 교체 호스트에서 웜, 콜드, 교체 복구 HTTP 흐름이 각각 검사 20건·요청 29건을 통과했다. 소스와 적용된 핵심 설정 해시 47개가 일치했다. 실제 교체 복구 실험 1회는 234.52초였고, 보존 대상 6건은 해시가 일치했으며 철회 대상은 나타나지 않았다.
- **한계:** EC2 한 대와 SQLite는 고가용성이 아니다. 한 번의 합성 복구는 대표 부하, 다중 호스트 장애, 운영 SLA 또는 모든 복구 시점의 안전성을 입증하지 않는다.
- **다음 트리거:** 사용자 수, 동시성, 복구 목표 또는 비동기 작업량을 먼저 측정한다. 그 측정치가 관리형 DB, 큐, 스트리밍 플랫폼의 운영 비용을 정당화할 때만 구성을 키운다.

### 철회 권한과 백업 복구 경계

- **문제:** 오래된 데이터베이스 백업을 복원해도 삭제·철회된 기록이 되살아나지 않아야 했다.
- **관측·원인:** 앱이 권한 상태를 직접 바꿀 수 있으면 데이터 경계가 넓어지고, 백업 안의 오래된 철회 정보가 최신 상태를 덮을 수 있다.
- **대안:** 앱에 DynamoDB 직접 쓰기를 허용하거나 삭제 권한을 SQLite에만 두는 방식은 각각 임의 갱신과 오래된 복원 위험을 남긴다.
- **선택 이유:** 앱 역할에 DynamoDB 직접 쓰기 권한을 주지 않고, Lambda가 조건부로 불변 삭제 의도를 추가하며 소유자·epoch를 비교하도록 권한을 제한했다. 트랜잭션 안의 쓰기 권한은 DynamoDB [트랜잭션 IAM 조건](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html)에 맞춘다. 권한 정보가 없거나 오래됐거나 소유자가 다르면 복원을 제공하지 않는 흐름을 택했다.
- **구현:** 복구는 검증한 S3 버전의 격리 사본에 최신 삭제 이력을 적용한 뒤 서비스 저장소와 교체하도록 구성했다. [복구 구현](../../app/cloud_rehearsal.py), [삭제 권한 구현](../../app/cloud_deletion_authority.py).
- **재검증:** 교체 복구 뒤 보존 대상 6건의 해시가 일치했고 철회 대상은 없었다. 손상된 백업 거부 및 앱의 직접 제어 쓰기 거부도 리허설 경로에서 확인했다.
- **한계:** 단일 실행은 모든 IAM·저장소 장애와 경합, 손상 형태를 다루지 않는다. 법률 내용과 사용자 결과도 측정하지 않았다.
- **다음 트리거:** 새 실행 전 권한 장애를 실제로 관찰할 수 있는 검증 수단을 준비하고, 경합·부분 실패 조건을 더한 독립 리허설을 설계한다.

### 콜드스타트 응답 시간

- **문제:** 최초 콜드스타트 철회 요청은 약 5,868ms 뒤 503을 반환했다.
- **관측·원인:** SDK 읽기 제한은 5초였고 Lambda 실행 제한보다 먼저 끝났다. 이 요청에서는 HTTP 실패 응답 뒤 원격 삭제 의도가 저장되어 다음 앱 guard가 반영했다.
- **대안:** SDK 제한만 유지하면 서버 작업이 완료되기 전에 클라이언트가 포기할 수 있었다. 반대로 제한만 늘려도 콜드스타트 여유가 부족할 수 있었다.
- **선택 이유 및 구현:** Lambda 읽기 제한을 15초, HTTP 클라이언트 제한을 20초로 조정하고 메모리를 128MiB에서 256MiB로 올렸다. 이는 시간 제한과 자원 설정을 함께 바꾼 지연 대응이다.
- **재검증:** 이후 관측은 invocation 2,789.76ms, 초기화 98.96ms였다. 웜·콜드 흐름도 각각 20검사·29요청을 통과했다.
- **한계:** 제한 시간과 메모리를 함께 바꾼 단일 재실행이므로 어느 변경이 차이를 만들었는지 분리할 수 없다. P95/P99, 꼬리 지연, 성능 향상 또는 SLA의 근거가 아니다.
- **다음 트리거:** 반복 표본과 부하를 모아 지연 분포를 측정한 뒤에만 개별 설정의 효과를 판단한다.

### 재시작과 SQLite crash recovery

- **문제:** 첫 재시작 검증은 HTTP 검사 0건을 반환했고, SIGKILL 뒤에는 헤더가 비어 있는 SQLite rollback journal이 남아 엄격한 시작 검사가 실패했다.
- **관측·원인:** 검증기가 프로세스 시작을 endpoint 준비 완료로 오인했다. 별도로 SQLite는 강제 종료 뒤 journal을 남길 수 있지만, 시작 허용 검사가 SQLite 자체 복구 전에 파일을 거부했다.
- **대안:** 준비 상태를 기다리지 않고 검사하거나 journal을 직접 삭제하면 성공을 잘못 세거나 복구 데이터를 버릴 수 있었다.
- **선택 이유 및 구현:** 제한 시간이 있는 readiness 대기로 endpoint 응답 뒤에만 검사한다. journal은 수동 unlink하지 않고 SQLite가 판단하는 guarded recovery를 먼저 수행한 뒤 strict startup 검사를 유지한다. systemd 재시작 제한 설정도 `[Unit]`에 두도록 바로잡았다. [서비스 설정](../../infra/rehearsal/systemd/youth-law-rehearsal.service).
- **재검증:** 교체 호스트에서 SIGKILL 뒤 자동 재시작 1회와 readiness 통과를 관찰했다. SQLite 복구 후 strict startup 및 철회 반영 흐름도 통과했다.
- **한계:** crash 지점과 호스트의 제한된 표본이다. 모든 종료 시점과 반복 재시작에서 복구된다는 보장은 아니다.
- **다음 트리거:** 지원할 crash 경계를 늘려 반복 실행하고, 복구 전후 저장소 불변조건을 검사한다.

### 권한 경로 장애 주입

- **문제:** 권한 저장소를 읽을 수 없을 때 앱이 fail-closed하고, 경로 복구 후 정상 상태로 돌아오는지 확인해야 했다.
- **관측·원인:** IAM 거부 probe에서는 60초 동안 예상한 차단이 관찰되지 않았다. readiness와 인증 상태가 200을 반환했다. 차단이 관찰되지 않은 원인은 미확정이다.
- **대안 및 선택:** 권한 오류로 단정하거나 네트워크 결과를 IAM 시험 결과처럼 쓰지 않았다. 별도로 UID 1001 프로세스의 외부 TCP 443 전체를 차단해 앱의 실패·복구 반응을 확인했다.
- **구현·재검증:** 전체 외부 TCP 443 차단 동안 readiness와 인증 상태는 503, 규칙 제거 뒤에는 200이었다. 관측된 회복 시간은 약 27.285초였다. 운영자 SSM 경로는 장애 주입 대상에서 제외했다.
- **한계:** 이는 DynamoDB 단독 장애 재현이 아니며 IAM 정책 거부도 증명하지 않는다. IAM probe의 정책 정리 단계가 통과했어도 차단 원인은 여전히 알 수 없다.
- **다음 트리거:** IAM 차단을 검증하려면 차단 전제와 관측 수단을 먼저 검증한 별도 실행이 필요하다. 그렇지 않으면 이 항목은 미확정으로 둔다.

### 백업 신선도와 자원 정리

- **문제:** 복구 실험에서 백업의 시점을 확인하고, 끝난 뒤 리허설 자원과 데이터가 남지 않았음을 점검해야 했다.
- **관측·원인:** 마지막 복구 실험은 장애 주입 전에 의도적으로 새 백업을 만들었다. 복구 시점의 백업 나이는 3.44초였다.
- **선택 이유 및 구현:** timer는 5분 간격으로 설정했고 백업 신선도 한계는 15분으로 두었다. 종료 절차는 S3 버전과 미완료 업로드를 정리한 다음 DynamoDB 삭제 권위를 마지막에 제거하도록 순서를 정했다.
- **재검증:** 교체 복구 1회는 234.52초였다. Terraform destroy는 31개 항목에 적용됐고, 최종 잔여 감사는 점검 37항목·오류 0·잔여 0을 기록했다. S3 버전 26개를 제거했으며 남은 버전·삭제 마커·업로드는 0이었다.
- **한계:** 31은 Terraform 제거 항목 수, 37은 감사 점검 수이며 고유 실물 자원 수가 아니다. 새 백업을 직전에 만든 3.44초 관측은 통상 RPO나 15분 RPO 보장이 아니다. 비용 청구 반영도 즉시 상태와 같지 않을 수 있다.
- **다음 트리거:** 다른 AWS 실행은 새 범위, 비용 한도, 종료 시각과 정리 점검 계획을 먼저 확정한 뒤 시작한다.

## 증거와 검증 범위

검토 가능한 요약은 [비식별 증거 JSON](../evidence/aws-rehearsal-20261021.json)에 있다. 당시 스냅샷은 전체 로컬 회귀 408건 통과(경고 5건), Python 3.12 집중 회귀 100건 통과, Ruff 통과를 기록한다. 이 숫자는 AWS 실행, 법률 품질, 사용자 결과 또는 독립 전문가 검토를 대신하지 않는다. JSON의 해시는 공개 대상 소스 파일의 내용 식별에 쓰이며, 원시 AWS 출력이나 개인 식별자를 공개하지 않는다.

**검증 시점의 경계:** 실행 당시에는 Terraform `main.tf`를 포함한 핵심 소스·유닛 해시 47개가 배포 스냅샷과 일치했다. 이후 [Terraform 소스](../../infra/rehearsal/main.tf)는 포맷 정리로 공백이 바뀌어 현재 파일의 바이트 해시는 실행 증거에 저장된 값과 다르다. 과거 해시는 실행 당시 기록으로 그대로 둔다. 또한 후속 코드 리뷰에서 앱 event loop의 직접 DynamoDB 호출 경로가 발견되어 수정 및 통합 검증 대상이 됐다. 이후 코드·문서 통합 검증은 AWS 재실행과 별도 증거이며, 원래 408개 테스트 기록이나 AWS 관측이 수정된 소스 버전까지 검증했다고 보지 않는다.

[공개 전 검토 기록](../evidence/aws-rehearsal-publication-20261021.json)은 이후 소스 해시와 로컬 회귀 검사를 별도로 남긴다. 전체 회귀 412건과 Python 3.12의 클라우드·비동기 경로 검사 61건이 통과했다. 느린 권한 조회 중에도 다른 HTTP 요청이 응답하고, 권한 확인 실패 시에는 503으로 보류되는지 확인했다. 이 변경은 AWS에서 다시 실행하지 않았으며, 원래 배포·복구 관측과 구분한다. 이후 변경도 PR에서 Python 3.11·3.12 테스트와 AWS 자격증명 없이 Terraform 검증을 실행한다.

전문가 검토는 PENDING, 실제 참여자 admission은 CLOSED다. 사용자 이익은 측정하지 않았다. 재개를 논의할 때는 동의·안전 범위, 전문가 검토 계획, 비교 가능한 사용자 결과 측정 기준을 먼저 정한다.

# 금융 첫 상담 준비와 삭제 이력을 지키는 복구

## 해결하려는 문제

법률 답변을 읽어도 첫 상담 전에 어떤 내용을 확인하고 무엇을 준비해야 할지 다시 정리해야 한다. 금융 문제를 처음 겪는 청년이 공식 문의 경로와 확인 사항을 한 번에 살펴보도록 상담 준비 카드를 추가했다. 실제로 검색이나 범용 챗봇보다 준비 부담을 줄이는지는 사용자 비교로 확인해야 하며, 현재는 전문가 검토 대기·실제 참가자 접수 닫힘 상태다.

팀 프로젝트의 법령 검색·분야별 Agent와 개인 후속 개발을 구분한다. 준비 카드는 공식 안내 카탈로그에서 고정 항목을 구성한다. 기존 RAG의 생성 답변, 근거 충족 검사, 카드의 사용성을 하나의 점수로 합치지 않는다.

## 복구에도 삭제를 반영하는 이유

동의와 관찰을 삭제했더라도 삭제 이전 DB 백업을 복원하면 해당 행이 돌아올 수 있다. 같은 DB에만 철회 상태를 저장하면 철회 이력도 함께 과거로 돌아간다. 복구한 자료를 서비스에 연결하기 전에, 별도로 보관한 최신 삭제 이력을 적용하도록 구성한다.

```text
철회: 최소 삭제 이력 내구성 기록 → DB 동의·관찰 삭제
복구: 서비스 수명 잠금 → 백업의 격리 사본 검사
       → 최신 삭제 이력 적용 → 무결성·남은 기록 확인
       → 검증된 DB만 교체 → 새 로그인 후 사용
```

삭제 이력은 요청 키 해시와 최초 만료 시각만 다룬다. 동의 내용·관찰·연락처·원래 요청 키를 복제하지 않는다. 복원 대상 DB와 이력·checkpoint의 경로는 다르다. 이력을 확인할 수 없거나 파일이 손상됐거나 기대한 최신 상태와 다르면 복구를 거절한다.

## 운영 경계

- 서비스는 공유 수명 잠금을 유지한다. 복구·초기 이관은 배타 잠금이 필요하므로 사용 중인 저장소를 덮어쓸 수 없다.
- 삭제 의도 기록 뒤 DB 처리가 중단되면 재시작 때 다시 적용한다. 최신성이 불명확한 상태를 빈 이력으로 바꾸지 않는다.
- 이력을 쓴 직후 checkpoint 갱신이 중단된 경우, 기존 checkpoint에 정확히 이어지는 완전한 행만 검증해 반영한다. 잘린 행이나 연결되지 않는 이력은 거절한다.
- 만료 이력 정리는 교체 전·후 세대의 지문을 남긴 뒤 진행한다. 중단 후에는 확인된 이전 세대를 유지하거나 완전한 새 세대의 게시를 마친다. 상태 조회도 쓰기 작업과 같은 잠금으로 직렬화한다.
- 기존 형식은 현재 신뢰한 DB 지문을 지정하는 명시적 이관이 필요하다. 설치 이전에 이미 유실된 철회 이력을 복구하지는 못한다.
- 새 자료는 저장소 식별자를 백업 DB에도 보관한다. 다른 저장소의 사본은 정책이 같아도 채택하지 않는다.
- 원본 백업은 수정하지 않고 별도 사본을 검증한다. 검증 실패 시 현재 DB를 교체하지 않는다.
- 동의·관찰과 차단 해시의 최초 보관 기한은 연장하지 않는다. 만료한 해시는 정리하고, 오래된 백업의 만료 행도 제공하지 않는다.

## 복구할 때 확인할 순서

1. 복원할 DB와 현재 삭제 이력을 구분한다. 이력까지 백업 시점으로 덮어쓰지 않는다.
2. 같은 저장소를 쓰는 서비스를 모두 종료한다. 새 서비스는 수명 잠금으로 충돌을 막지만, 이전 버전 프로세스에는 이 잠금이 없으므로 최초 이관 전에 별도로 종료를 확인해야 한다.
3. 현재 정책 파일과 삭제 이력의 checkpoint를 확인한다. 기존 형식의 최초 이관에는 현재 DB의 신뢰한 SHA-256과 `--confirm-legacy-services-stopped` 확인이 필요하다. 이 옵션 자체가 구버전 프로세스의 종료를 증명하지는 않는다.
4. `restore` 명령에 원본 백업과 확인한 `--expected-ledger-checkpoint`를 지정한다. 저장소 식별자가 없는 구형 백업은 자동 채택하지 않는다. 검증 실패 시 파일을 지우거나 빈 이력으로 재생성해 우회하지 않는다.
5. 재시작 후 새로 로그인해 철회 기록은 조회되지 않고, 유지할 기록은 관찰 내용과 버전이 같은지 확인한다. 실제 참가자 접수 상태도 다시 확인한다.

복구 명령은 격리 사본에 먼저 삭제 이력을 적용한다. 백업을 직접 서비스 경로에 복사하는 절차는 이 검증을 건너뛰므로 사용하지 않는다.

## 검사 재현

프로젝트 루트의 Python 환경에서 실행한다. 더미 검사에는 외부 모델이나 AWS 계정이 필요하지 않다.

```sh
python -m pytest -q tests/test_participant_recovery.py
python scripts/check_rehearsal_runtime.py --report /tmp/rehearsal-runtime-new.json
python -m app.participant_recovery --help
```

삭제 전 백업, 철회한 기록과 유지할 기록, 삭제 의도 기록 뒤 실패, 이력 누락·손상·불일치, 실행 중 복구 거절, 복구 반복, 만료 처리를 검사한다. 실제 DB·정책·토큰·관찰 원문은 공개하지 않는다. 실제 운영자 명령은 별도의 비공개 경로와 검토된 정책 파일이 필요하다.

2026-10-21 공개 후보에서 기존 계약을 포함한 `pytest tests/` 349개와 Ruff 검사를 통과했다. 실제 loopback HTTP 검사에서는 인증, 요청 제한, 동시 요청 1·4·8개, 재시작, 삭제 전 백업 복구 등 47개 시나리오를 확인했다. [더미 실행 결과와 소스 지문](evidence/rehearsal-runtime-20261021.json)을 함께 남긴다. 메모리는 주기적으로 관찰한 값이며 최대 메모리나 운영 SLO의 보장이 아니다.

테스트 환경은 기존 Python 3.11 가상환경을 사용했다. `httpx`는 검증한 버전으로 고정했지만 전체 의존성을 잠근 환경은 아니다. 기존 FastAPI startup 이벤트와 Starlette의 `httpx` TestClient 연동에 대한 폐기 예정 경고가 남아 있으며, 의존성 교체는 별도 호환성 검사가 필요하다.

## 검증 범위

이 구조는 DB만 과거 사본으로 복구하면서 현재 삭제 이력을 유지하는 경계다. 같은 OS 소유자가 이력과 checkpoint까지 함께 과거 상태로 바꾸면 로컬 기준만으로 최신성을 입증할 수 없다. 공유·클라우드 환경에는 별도 권한과 독립된 최신성 기준이 필요하다.

SQLite 논리 삭제와 디스크·APFS·다른 사본의 완전 삭제는 다르다. 공개 사용자 인증, 장기 부하, 클라우드 가용성, 법률 정확성이나 사용자 효과를 이 더미 검사로 주장하지 않는다. 이미 표시된 다른 브라우저 화면은 새로고침하거나 닫아야 한다.
